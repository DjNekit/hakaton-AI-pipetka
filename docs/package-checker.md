# Проверка пакета по чек-листу

Пункты исходного `Примеры чек-листов.xlsx` импортированы в `package_checklists`
в `checker/colorpass/data/rules.yaml`: 6 общих, 2 специальных, по 14 для паспортов и вывесок,
30 для архитектурных решений. Сохраняются оригинальные формулировки, строки и SHA-256 источника.
Изменённые пороги/правила не следует считать подтверждёнными текстом постановлений без сверки первоисточника.

## Использование

В обоих интерфейсах выберите вид услуги и загрузите проект с приложениями одним пакетом.
Новый интерфейс принимает до 20 PDF по 50 МБ; основной интерфейс также принимает JPEG/PNG.

API: сначала `POST /files/uploads` (multipart `files`), затем:

```json
{
  "uploads": [{"id": "<id загрузки>", "name": "проект.pdf", "kind": "pdf"}],
  "service_type": "passport",
  "title": "Адрес объекта"
}
```

`POST /api/packages` возвращает 202. `service_type`: `passport`, `signage`, `facade`.
Опрос: `GET /api/packages/<id>` до `state: done`. Поле `checks` содержит пункты:
`rule`, `section`, `title`, `requirement`, `ref`, `status`, `verdict`, `note`,
`source` (книга, лист, диапазон, SHA-256), `evidence` (документ, страница, цитата/правило),
`missing_data` (если указано в конфигурации).

`ok` — подтверждённая техническая проверка; `fail` — выявленное нарушение;
`warn` / `verdict: unknown` — частичные подтверждения или недостаточно данных.
Найденное ключевое слово не доказывает полноту раздела или соответствие всей норме.
Без проверенной применимости пункт не получает «не применимо».

При выбранной услуге каждый PDF извлекается как часть пакета, без требования содержать полный проект.
Для паспортов и вывесок листы объединяются в порядке загрузки, существующие формализованные проверки
выполняются на сводном документе; номера листов в доказательствах переводятся обратно в исходные PDF.
В пунктах с текстовыми признаками подтверждения ищутся по всем документам пакета.
Результат также сохраняется в `runs/packages/<id>/report.json`, сводный технический отчёт — в `combined/`.
Если `service_type` не указан, сохраняется прежняя проверка каждого документа с автоопределением вида.

В новом интерфейсе демо-генерация заменена реальным вызовом checker через backend и Redis.
Идентификатор пакета хранится в заявке; заявки `ai_check` (и прежние `review`) с незавершённой автоматической проверкой
возобновляют ожидание при старте applications-api. Модель не принимает решение.
После автоматической проверки заявка переходит в `review`. Согласующий заполняет ручной чек-лист из того же каталога checker
(`GET /new/api/applications/<id>/checklist`), не видя автоматических ответов.
После отправки ручной проверки заявка переходит в `normcontrol`: нормоконтролёр видит
сравнение результатов и принимает итоговое решение.

## Границы реализации

Автоматические нормативные проверки сейчас реализованы для паспортов/вывесок и сопоставлены
с соответствующими пунктами Excel. Они покрывают лишь часть требований даже этих пунктов.
По 94-ПП пока извлекаются текстовые подтверждения состава проекта, но геометрия, применимость,
согласования и правовой статус не проверяются автоматически. Такие пункты остаются у инспектора.
Фотографии пакета доступны для сравнения; сам факт загрузки фото не доказывает его дату и соответствие проекту.

Необходимые первоисточники и данные перечислены в `dataset/regulations/README.md`.
Исходный Excel хранится в `dataset/checklists/`. Повторный импорт:

```bash
python3 scripts/import_package_checklists.py 'dataset/checklists/Примеры чек-листов.xlsx'
```

Импорт обновляет каталог, сохраняя настройки `package_evidence`. После изменения правил перезапустите checker
(конфигурация кэшируется в процессе).

### Пояснения GigaChat к чек-листу

После готовности формального отчёта новый клиент запускает `POST /chat/packages/:id/checklist` через applications-api. Сервис chat отбирает до трёх текстовых фрагментов для каждого пункта и отправляет до шести пунктов одним запросом. Пункты, требующие внешних сведений (`missing_data`), передаются инспектору без вызова модели. Модель готовит пояснения и предложения для ручной проверки, без нормативного вердикта. Цитата принимается только при дословном совпадении с переданным фрагментом; номер страницы и имя документа подставляет код.

Разбор сохраняется в PostgreSQL отдельно от `checks`, в `package.checklist_review` через `/api/packages/:id/checklist-review`. Хеш учитывает профиль, пункты, документы, завершение формальной проверки, модель и версию промпта. Параллельные вкладки используют одну задачу. Прогресс сохраняется после каждой группы; после перезапуска или явного повтора выполняются только оставшиеся пункты. Ошибка GigaChat сохраняет формальные результаты и уже готовые пояснения. Повтор разбора доступен заявителю; согласующему автоматические пояснения не раскрываются.

Очередь chat обрабатывает один пакет за раз. Вызовы модели выполняются только из chat. Backend не открывает PDF; контекст берётся из отчётов checker. Этот этап работает по извлечённому тексту, не заменяет визуальную проверку чертежей и проверку внешних реестров.
